# Контейнеры и графика

## Общий контейнер — разобрано

`mesh.dat`, `textures.dat`, `materials.dat`, `objects.dat`, `boxes.dat`,
а также `objects2.dat`, `rdata.dat`, `ctrlobj.dat` начинаются одинаково:

```
u32 magic
u32 count
u32 dataBytes
u32 nameTableBytes
count × { u32 hash, u32 nameOffset, u32 size, u32 offset }  // по hash
... тела записей ...
таблица имён (cp1251, NUL) в самом конце файла
```

Магики, которые встретились:

| Магик | Где | Записей (игра 1 → игра 2) |
| --- | --- | --- |
| `DATA` | меши, `gdata`, `boxes`, `objects2`, `rdata`, `ctrlobj` | зависит от файла |
| `MEOS` | `objects.dat` | узлы техники |
| `TEXS` | `textures.dat`, `ctrltex.dat`, `atextures.dat` | текстуры; во второй игре `atextures.dat` — 714 имён |
| `DMAT` | `materials.dat` | материалы |
| `PARS` | `particles.dat` | 206 имён в первой игре |
| `DXMC` / `DXMC2` | `dxm.dat` | 49 профилей рендера в первой игре. Во второй магик `DXMC2` |
| `PICS` | `pictures.dat` | 46 картинок меню первой игры |

`PICS`, `PARS`, `DXMC` имеют тот же заголовок из четырёх `u32` и таблицу имён
в конце. Тела записей не читались, кроме того, что имена осмысленны
(`ExitA`, `AAMLExpl2`, `terrain_light`, `std_transp_add`).

Реализация контейнера — `Container` в `tools/legacy_export.py`.

## Две системы координат оригинала — разобрано

Движок ремейка сам оси не переворачивает. Эталон — `ech::meshToEngine` и
`ech::d3dToEngine` в `src/core/include/echelon/math/frame.hpp` (тест
`tests/frame_test.cpp` на `ViewDelta`, `BackViewDelta` и узле стекла BF-1).
`tools/legacy_export.py` (`to_engine`, `d3d_to_engine`) повторяет их и не должен
расходиться.

1. **Вершины `mesh.dat`** — правая система с «верхом» по −Y: X вправо, **Y вниз**,
   нос +Z, левая сторона −X (фонарь и голова пилота в −Y). Это система ремейка
   (X вправо, Y вверх, нос −Z), повёрнутая на 180° вокруг X. `to_engine`:
   `(x, y, z) → (x, −y, −z)`. Это **поворот, не зеркало**: порядок индексов
   треугольников не меняется, лицевые грани остаются против часовой.
   Экспортёр сверяет каждый треугольник с нормалями (`_faces_normal`) и печатает
   `!` с числом несогласованных; ненулевое значение — ошибка индексации или осей,
   а не повод переставлять индексы. Текстурные координаты: `v → 1 − v`
   (согласовано с `stbi_set_flip_vertically_on_load(1)`).
2. **Всё остальное** (`objects.dat` — позиции узлов; `gdata.dat` — `ViewDelta`,
   `BackViewDelta = (0, 1, −6)` «выше и сзади», `Position`; точки подвески) —
   классическая левая система D3D: X вправо, **Y вверх**, нос +Z. `d3d_to_engine`:
   `(x, y, z) → (x, y, −z)`. Проверка: bbox узла `CoPilot` в `objects.dat`
   совпадает с bbox меша после инверсии Y; узел стекла ложится на интерьер
   `kabina`.

Отвергнутые варианты, к которым не возвращаться: `z → −z` плюс перестановка
индексов `(t0, t2, t1)` для вершин (модель оказывается вверх ногами и зеркальной);
`to_engine` для позиций узлов (детали зеркалятся по вертикали).

Для новых данных из оригинала (точки подвески, координаты объектов миссий,
повороты) использовать `d3dToEngine`. При зеркале Z углы вокруг X и Y меняют
знак, вокруг Z — нет. Координаты мира миссий этой проверкой не покрыты.

## Меш — разобрано для `Im`/`Ld`, то же тело у `Img`/`Lod`

Запись `<file>_<part>_Im<damage>_Ld<lod>`:

```
u32 0, nSubsets, nMaterials, 1
f32 sphere x, y, z, r
nMaterials × { u32 flags, u32 textureHash, u32 materialHash, u32 0 }
nSubsets × { u32 prim=4 (trilist), u32 mat, u16 firstVertex, u16 vertexCount, u32 indexCount }
u32 ?, u32 totalVerts, u32 crc
u16 indices
```

**Индексы каждого сабсета считаются от его `firstVertex`.** Если читать их как
абсолютные, все сабсеты кроме первого собираются из чужих вершин («шипы») и
выглядят как сломанный обход. Вершины лежат отдельной записью `<...>_V00`
(у `ha_hvy4` — `<...>_Vert00`): 32 байта `{ f32 pos[3], normal[3], uv[2] }`.

`Im0`/`Im1`/`Im2` — состояния повреждений; у кабины и `CoPilot` бывает ещё
`Im3`. `Ld0`… — LOD. `textureHash = 0xFFFFFFFF` — сабсет без текстуры (стекло).
У части машин фюзеляж записан без имени части (`ha_bf2_Im0_Ld0`); экспортёр
называет такую часть `HULL`.

Ненулевой `_faces_normal` уже встречался и оставлен предупреждением, без
перемотки индексов: `ha_bf1` RE Im2 (4 треугольника), `ha_bf4` cockpit Zhopa
Im3 (12), `ha_hvy3` cockpit Im0 (7), `ha_sf1` cockpit Im0–Im2 (36).

У вельянских корпусов **другой шаблон имени**, тело то же. Сверено на
`ha_bf1_cockpit_Im0_Ld0` и `va_bf1_Img0_Lod0`: оба начинаются с
`u32 0, nSubsets, nMaterials, 1` и сферы. Примеры имён:

```
va_bf1_Img0_Lod0
va_bf1_Img0_Lod0_Vert00
va_int2_Glass_Img0_Lod0
```

`Img` / `Lod` / `Vert` вместо `Im` / `Ld` / `V`. Экспортёр ищет только
`Im`/`Ld`, поэтому `Velian_BF1` и соседи пропускаются, хотя записи лежат в
`mesh.dat` первой игры (у `va_bf1` только в первой игре 300 записей). Во
второй игре тех же префиксов больше, появляется `va_sf1` и `va_bf2human`.

Конвертация осей для `Img`/`Lod` та же, что в разделе выше, но на собранной
модели вельян ещё не проверялась.

## Текстуры и материалы — разобрано

Текстура: заголовок 56 байт (`u32 size` по смещению 0, `width` по 16, `height`
по 20, FourCC по 48), затем цепочка мипов DXT1/DXT5. Декодер — `decode_dxt`
в экспортёре.

У BF-1 обшивка — `ha_bf1` (DXT1, 256×256). В `textures.dat` есть ещё `ha-bf1`
512×512 через дефис, та же раскладка; это единственная такая пара во всём
файле, меш ссылается на 256×256. `asrez` — срез сопла, `kabina` — кабина
(DXT5), `pil1m` — пилот. Альфа `kabina` в данных действительно нулевая
(`a0=0`, `a1=1`, во всех блоках биты 0) — это не ошибка декодера, и альфа
этой текстуры не используется.

Материал: 68 байт, раскладка `D3DMATERIAL7` — diffuse, ambient, specular,
emissive (по 4 f32 RGBA) и f32 power. Меш ссылается на материал по
`materialHash`. Четвёртый компонент diffuse — **не обычная альфа**: у BF-1
`Metal` 2.0, `RMetal` и `Cockpit` 0.0, `Glass` 0.4. Прозрачным в ремейке
считается только значение строго в (0, 1) (`Model::Subset::transparent`).
`RMetal` — срез сопла, `Cockpit` — кабина, `Glass` — стекло.

## `objects.dat` — разобрано частично

Запись корпуса (у BF-1 `ha_bf1`, 9852 байта; у BF-2 — 16503). Заголовок:
`u32 ×4 (2048, offA, offB, offNames)`, затем `f32 bbox (−x, −z, +x, +z)`.
Дальше узлы частей. На каждое состояние урона 40 байт
`{ f32 bboxMin[3], bboxMax[3], radius, u32 ×3 }`, затем
`{ f32 position[3], forward[3], up[3], u32 }` и 8-байтовая метка (короткое имя
`HTNO`/`LD`/`RD`/`LV`/`RV` или хеш).

**Позиция и базис — относительно родителя.** Родитель выводится из имени меша:
`LE_LW` висит на `LE`, `cockpit_glass` — на `cockpit`. Проверка на BF-1:
`2.838 + 3.548 + 2.133 = 8.519`, это полуразмах из заголовка. Bbox узла хранится
в системе Y-вверх, bbox меша — Y-вниз; сопоставление после
`(lo.x, −hi.y, lo.z, hi.x, −lo.y, hi.z)`.

Узлы бывают повёрнуты. У BF-1 базис единичный (`forward=(0,0,1)`, `up=(0,1,0)`).
У BF-2, BF-3 и HVY крылья лежат с `forward=(0,1,0)`, `up=(0,0,−1)`, у HVY3
углы не осевые. `parse_object_nodes` сканирует запись с шагом 4 байта и принимает
любую ортонормированную пару. Те же числа читаются ещё и на 4 байта позже —
это ложное эхо, берётся более ранний узел. Узлы без bbox — точки подвески,
для частей не используются.

Сопоставление с мешами — `assign_nodes`: жадное один-к-одному по bbox
(допуск 0.25). Зеркальные пары LE/RE различаются знаком X узла и буквой L/R
в имени. Размещение — композиция по цепочке имён до корня
(`absolute_transform`): `pos = pos_parent + R_parent·local`,
`R = R_parent·R_local`. Поворот переводится в систему ремейка сопряжением
`D·R·D`, `D = diag(1,1,−1)` (`_d3d_rotation_to_engine`) и пишется в JSON как
кватернион `orientation: [x, y, z, w]`.

BF-1, узлы в системе D3D относительно родителя. Фюзеляж хранится как часть
`cockpit`: `LE`(−2.84, −0.25, −2.98), `RE`(2.88, −0.25, −2.98),
`LW`(−3.55, −0.94, 0.62) от `LE`, `RW`(3.53, −0.94, 0.62) от `RE`,
`glass`(−0.04, −0.35, 3.97), `Pilot`(−0.07, −0.68, 4.89),
`CoPilot`(−0.03, −1.46, 0), `cockpit`(0.07, 0.06, 0).

В хвосте записи — имена точек подвески (`MEDIUMA`, `SMALLA`, `ROCKETA`/`B`,
`Duza*`). Их позиции **ещё не разобраны**; они нужны для стрельбы и струй сопел.

`objects2.dat` — отдельный `DATA`-контейнер (461 имя в первой игре):
`bunker3`, `railroadbridge600m_part`, `va_hvy2`, `smallshell`. Это статичные
объекты мира, не узлы самолёта. Формат тела записи не сравнивался с мешем.

## `boxes.dat` — каталог

Коллизия по частям: сфера и набор плоскостей, не матрицы. В ремейке не читается.
