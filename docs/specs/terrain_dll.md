# `Terrain.dll`

Разбор `legacy/Echelon/Terrain.dll` (17 апреля 2001, линкер MSVC 6.00, 28 672 байта,
PE32, база `0x10000000`, символов нет). Раскладка файлов карты — в
[terrain.md](terrain.md); здесь только то, что делает сама DLL. Вторая игра —
коротко в конце.

Уверенность помечена в тексте: **проверено** — адрес и сверка с файлом или
с уже принятой формулой; **гипотеза** — смысл, который из кода не следует
однозначно.

## Назначение и границы

DLL отдаёт данные ландшафта и запросы к ним. Рисования в ней нет.

Импорт первой игры: `MadTools` (`_HFILE::Open/Read/Write/Close`, `OpenMapFile`,
`PLANE::ClipVector`) и `USER32!wsprintfA`. Ни DirectDraw, ни текстур, ни
вершинного буфера. Точка входа в таблицу экспорта не вынесена: с `0x10001000`
сразу идут функции `TERRAIN_DATA`.

Кто вызывает (**проверено** по таблице импорта):

| Модуль | Что берёт из `Terrain.dll` |
| --- | --- |
| `StormGame.dll` | `Open`, `OpenSq`, `OpenBx`, `OpenVb`, `Close`, `GroundLevel` (вариант с `TraceResult`), `GroundLevelMedian`, `WaterLevel` (вариант с `TraceResult`) |
| `Renderer.dll` | `GroundLevel` (вариант с `TraceResult`), `OpenLight` |
| `HashTools.dll` | `TraceLine`, `GroundLevel` (вариант с `TraceResult`), `WaterLevel` (вариант с `TraceResult`) |

`Standart.ai` `Terrain.dll` не импортирует. Строки `AvoidTerrain` и
`HangarStatus` лежат в `StdLogic.ai` второй игры — это имена поведения ИИ, не
экспорты и не функции этой DLL. `DRAWTERRAIN` — строка настройки в `Game.exe`
(первая игра) и `Menu.dll` (вторая), не символ `Terrain.dll`. Кадр земли
собирает `Renderer.dll` (у него же строка `terrain_light`).

LOD, морфинга и выбора уровня детализации в DLL нет: ни констант переключения,
ни второй геометрии, ни пути «далеко → реже». Единственная иерархия — ускорение
луча: ячейка 256 м (`.bx`), внутри неё квад 64 м (`.sq`).

вызываемый (`ret N`). `QBE` в декорированном имени — метод `const`. `bool` на
стеке занимает 4 байта, читается как байт.

| 14 | `10002850` | `bool TraceBoxLine(VLine const&, TraceResult*, float, float, T_BOX const*, T_VBOX const*) const` |

`Open` только читает заголовок. `StormGame` следом сам вызывает `OpenSq`,
`OpenBx`, `OpenVb`. `Create` делает все три вызова и записывает `.hd`.

Два `bool` у `OpenSq` / `OpenBx` / `OpenVb` / `OpenLight` складываются в режим
`OpenMapFile` (**проверено** арифметика, **гипотеза** смысл чисел):

```
mode = (arg1 ? 1 : 0) + (arg0 ? 0 : 2)
```

`Create` зовёт их как `(false, true)` → режим 3. В слот пишется флаг
`arg1 ? 1 : 2`. Имена режимов `OpenMapFile` в этой DLL не закодированы.

### `VLine` — проверено по чтениям

`ClipLine` и трассировка читают два `VECTOR` и предел параметра:

| Смещение | Поле |
| --- | --- |
| `+0x00` | начало, X |
| `+0x04` | начало, Y |
| `+0x08` | начало, Z |
| `+0x0C` | направление, X |
| `+0x10` | направление, Y |
| `+0x14` | направление, Z |
| `+0x18` | дальний `t` (`TraceLine` подставляет его, если отрезок не обрезан) |

Точка на луче: `origin + t * direction`. Оси — D3D, как у сетки в
[terrain.md](terrain.md): X — столбец, Z — строка, Y — вверх.

### `TraceResult` — проверено по записям

| Смещение | Поле |
| --- | --- |
| `+0x00` | `int` тип: `2` — земля, `3` — плоская вода |
| `+0x04` | позиция X (`GroundLevel` / `WaterLevel` с результатом) |
| `+0x08` | позиция Y |
| `+0x0C` | позиция Z |
| `+0x10` | высота в метрах у запросов уровня; параметр `t` у трассировки |
| `+0x14` | первый компонент ориентации поверхности |
| `+0x18` | второй; у плоских попаданий это `1.0`, у квада сюда кладётся `64` |
| `+0x1C` | третий компонент |
| `+0x20` | `0` |
| `+0x24` | класс поверхности, биты 0–2 флагов `.sq`; у воды и у `TraceLineOut` — `0` |

Тройка `+0x14…+0x1C` у квада — не единичная нормаль. В неё пишутся перепад
высот и константа `64` (шаг сетки в метрах). **Гипотеза:** это сырой
касательный вектор ребра, его нормализует вызывающий.

`TraceSquareLine` заполняет тип, `t`, ориентацию, класс и `+0x20`. Позицию
`+0x04` пишет вариант `GroundLevel` / `WaterLevel` с `TraceResult`.

## Раскладка `TERRAIN_DATA`

**Проверено** по `Open` / `OpenSq` / `OpenBx` / `OpenVb` / `OpenLight` /
`Create` / `Close`. Размер объекта DLL не задаёт: буфер пути в конце без
проверки длины, память выделяет вызывающий.

Пять слотов отображённого файла, каждый 0x14 байт:

| Смещение | Слот | Содержимое |
| --- | --- | --- |
| `+0x00` | `.sq` | handle `OpenMapFile`, данные, `tilesX`, `tilesY`, флаг режима |
| `+0x14` | `.bx` | то же; счётчики — `chunksX`, `chunksY`, не плитки |
| `+0x28` | `.vb` | то же; счётчики — `chunksX*2`, `chunksY*2` |
| `+0x3C` | свет 0 | слот `OpenLight` при `slot == 0` |
| `+0x50` | свет 1 | слот `OpenLight` при `slot == 1` |

Внутри слота: `+0` handle, `+4` указатель на байты, `+8` и `+0x0C` размеры
сетки плиток, `+0x10` флаг `1` или `2`. `Close` отпускает все пять (виртуальный
вызов по handle, затем нули). Третьего слота света нет: индекс 2 попал бы на
заголовок `+0x64`.

Дальше — копия `.hd` и путь:

| Смещение | Файл `.hd` | Поле |
| --- | --- | --- |
| `+0x64` | `+0` | `chunksX` |
| `+0x68` | `+4` | `chunksY` |
| `+0x6C` | `+8` | 32 записи `{f32 x, y, z; u32 flags}`, 512 байт. Это направления солнца из [terrain.md](terrain.md); заняты первые 19 (`.l00`…`.l18`), хвост до смещения 520 — запас |
| `+0x26C` | `+520` | `u32` длина списка, в файлах `30` |
| `+0x270` | `+524` | `int[30]`, 120 байт. `Create` / `ResetHdr` зануляют 32 dword, включая два лишних по `+0x2E8` и `+0x2EC` |
| `+0x2F0` | — | `char*`, указывает на нулевой байт пути |
| `+0x2F4` | — | сам путь без расширения |

`Open` дописывает расширение в позицию `+0x2F0`. Отсюда же `OpenLight` печатает
`.l%02d` через `wsprintfA`.

Индексаторы получают `ecx`, указывающий на поле «данные» слота (`this+4` для
`.sq`, `this+0x2C` для `.vb`): по `[ecx]` лежит указатель, по `[ecx+4]` — число
плиток по X. Так `10001070` видит `tilesX`, хотя в объекте `tilesX` стоит на
`+8`.

## Алгоритмы

### `GroundLevel`

Мировая точка → индекс отсчёта (**проверено**, `10003200`):

```
i = (int)(x * (1/64) + (−0.5))     // double −0.5 по 100051A0, 1/64 по 1000519C
j = (int)(z * (1/64) + (−0.5))
```

Дробные доли `fx`, `fz` — остаток после `fist`. Индекс отсекается так, чтобы
существовал квад `(i, j)…(i+1, j+1)`: верхняя граница `tiles*32 − 2`.

Четыре высоты × `0.2` (`10005138`). Бит 15 флагов отсчёта `(i, j)` выбирает
диагональ. Формула — в [terrain.md](terrain.md), реализация `10003331`.
Вариант с `TraceResult` делает то же и дописывает тип `2`, позицию, тройку
ориентации и `flags & 7` в `+0x24` (`10003869`).

### `WaterLevel`

Сетка `.vb`, шаг 256 м = 4 отсчёта (**проверено**, `10003430` и `100038C0`):

```
u = x * (1/256) + (−0.5)     // 1/256 = 100051BC, double −0.5 = 100051C0 и 10005200
v = z * (1/256) + (−0.5)
```

Четыре угла ячейки, билинейно, значение × `0.2`. Это уровень из `i16` по
смещению +2 записи. Вариант с `TraceResult`: тип `3`, нормаль `(0, 1, 0)`,
класс `0`.

### `GroundLevelMedian`

Имя в экспорте — median, тело — среднее арифметическое (**проверено**,
`10003A80`). Прямоугольник отсчётов:

```
i0 = (int)((x − r) / 64 − 0.5) … i1 = (int)((x + r) / 64 + 0.5)
```

и то же для `z`. Сумма сырых `i16` × `0.2` / число отсчётов. Пустой
прямоугольник → `0`.

### `ClipLine`

Четыре вертикальные плоскости через `PLANE::ClipVector` (**проверено**,
`100022B0`). Прямоугольник карты в метрах — `[0, chunksX*128*64]` по X и
`[0, chunksY*128*64]` по Z, каждая грань сдвинута внутрь на 16 м (`10005060`).
Нормали `(±1,0,0)` и `(0,0,±1)`. Если отрезок не пересекает прямоугольник,
функция возвращает `false` и не трогает `float*`. Иначе в `float*` — параметр
входа.

### `TraceLine`

**Проверено** каркас, `100021D0`.

```
t0 = 0
t1 = line.tFar          // +0x18
if ClipLine(line, &t0):
    if t0 == 0:         // старт уже внутри прямоугольника
        if TraceLineIn(line, result, t0, t1): return true
        if t1 > line.tFar: return false
        return TraceLineOut(line, result, t1, line.tFar)
    return TraceLineOut(line, result, t0, 0)
return TraceLineOut(line, result, 0, line.tFar)
```

`TraceLineOut` (`10002410`) пересекает луч с плоскостью `Y = 0` (коэффициенты
нормали — нули по X и Z и `−1` по Y). Если `t` между двумя аргументами, пишет
тип `2`, нормаль `(0, 1, 0)`, класс `0`. Это запасной удар «снаружи сетки», не
квад рельефа.

### `TraceLineIn` — ячейки 256 м и `.bx`

**Проверено** `100024A0`. Классический сеточный обход (шаг ±1, `tDelta`,
`tMax`) по XZ. Размер ячейки 256 м: константы `256` (`100050E8`) и `1/256`
(`100050F4`). Если компонент направления почти ноль, шаг по этой оси —
`1e7` (double `100050E0`) или `FLT_MAX` (`100050EC`), эпсилон сравнения —
`1e-7` (`100050D0`).

Координата ячейки `(cx, cz)` — это индекс клетки 4×4 отсчёта. Указатель в
`.bx`:

```
index = ((cx & ~31) + (cz & ~31) * chunksX) * 32
        + (cz & 31) * 32 + (cx & 31)
box   = bxData + index * 4
```

`chunksX` берётся из слота `.bx` (`this+0x1C`). Та же координата адресует
запись `.vb` формулой из [terrain.md](terrain.md) (`N = chunksX*2`).

На каждой ячейке вызывается `TraceBoxLine`. Пока он возвращает `false`, обход
идёт дальше. `true` — попадание, `TraceLineIn` тоже возвращает `true`.

### `TraceBoxLine` — максимум ячейки, затем квад 64 м

**Проверено** `10002850`. Запись `.bx` — 4 байта, `T_BOX`:

| Смещение | Поле |
| --- | --- |
| `+0` | `i16` максимум высот × `0.2` даёт метры |
| `+2` | `i16` минимум тех же высот |

Окно — 5×5 отсчётов с угла `(4·cx, 4·cz)` включительно до `(4·cx+4, 4·cz+4)`.
Это как раз вершины 4×4 квадов ячейки. Сверка: NetArena, все 3206 неоднородных
ячеек; Continent, 6319 из 6319 проверенных. Первое слово нигде не меньше
максимума окна, второе нигде не больше минимума, и на этой выборке оба равны
им точно.

Луч на входе в ячейку (`t0`) и на выходе (`t1`): если **оба** Y строго выше
максимума, квады не смотрятся. Тогда два `i16` записи `.vb` по смещениям `+4` и
`+6` (тоже × `0.2`) задают вертикальный интервал. Попадание в него — тип `3`,
`t` на середину интервала, нормаль `(0, 1, 0)`. Иначе `false`.

Если хотя бы один конец не выше максимума, управление переходит в `10002944`:
такой же сеточный обход, но с шагом 64 м (`1/64` = `10005168`), и на каждой
клетке `TraceSquareLine` с целыми индексами отсчёта `(i, j)`.

Второе слово `.bx` (минимум) эта DLL не читает. Оно нужно разве что редактору
или сборке, которая отсекает луч ещё и снизу. **Гипотеза.**

Пара `+4`/`+6` в `.vb` на NetArena всегда `(0, 0)`, на Continent расходится с
уровнем воды примерно в 0.3% ячеек (например вода `−468`, слово `+6` =
`−2500`). Что пара означает в данных, код не объясняет: он использует её только
как интервал высот. Уровень воды для геймплея читает `WaterLevel` из `i16` по
`+2`.

### `TraceSquareLine`

**Проверено** каркас, `10002C40`. Четыре высоты квада `(i, j)`, бит 15 выбирает
диагональ — та же развилка, что у `GroundLevel`. Луч тестируется против
выбранного треугольника. Промах — `false` (`10002D7E`). Попадание — тип `2`,
`t` в `+0x10`, ориентация с компонентом `64`, класс `flags & 7`.

Полную арифметику пересечения с треугольником (около килобайта x87) по
именам регистров не восстанавливал. Входы и запись результата — проверены.

### `Zero`

**Проверено** `10001FC0`. Обходит каждую плитку и заполняет её константой.

| Слой | Запись | Значение |
| --- | --- | --- |
| `.sq` | `{i16, u16}` | высота `0`, флаги `0` |
| `.bx` | `{i16 max, i16 min}` | `−32768`, `+32767` |
| `.vb` | 16 байт | нули (четыре dword `1000502C…10005038`) |

У `.bx` максимум становится −6553.6 м, то есть грубый тест считает ячейку пустой
и до квадов не доходит, пока боксы не пересчитают. Пересчёта боксов в этой DLL
нет: `Zero` только заливает память.

## Чтение файлов

Общий приём для `.sq` / `.bx` / `.vb` / `.lNN` (**проверено**): дописать
расширение к пути, `OpenMapFile`, сверить размер с ожидаемым. Если не сошёлся,
виртуальный вызов `[vtable+0x10]` с нужным размером (по смыслу — дочитать или
растянуть; имя метода в `MadTools` отсюда не видно). Всё ещё не сошлось —
слот отпускается, функция возвращает `false`. Иначе в слот пишутся указатель и
размеры.

Ожидаемый размер:

| Файл | Расширение | Байт |
| --- | --- | --- |
| `.sq` | `100052C0` | `(chunksX*4) * (chunksY*4) * 4096` — плитка 32×32 отсчёта по 4 байта |
| `.bx` | `100052A0` | `chunksX * chunksY * 4096` — чанк 32×32 ячеек по 4 байта |
| `.vb` | `10005280` | `(chunksX*2) * (chunksY*2) * 4096` — плитка 16×16 записей по 16 байт |
| `.lNN` | `10005260` `".l%02d"` | `chunksX * chunksY * 4096` — те же 256 байт на плитку 32×32, что и у `.bx` по объёму |

`.hd` (`100052E0`) читается не через `OpenMapFile`, а через `_HFILE`:
`Open(path, false, 3)`, затем `0x20C` байт в `this+0x64` и ещё
`count*4` байт в `this+0x270`. Запись (`Create`, `ResetHdr`, `Close(true)`):
`Open(path, true, 2)` и `Write` тех же двух кусков. Смысл аргументов
`_HFILE::Open` за пределами этих двух вызовов не разбирался.

`OpenLight(arg0, arg1, slot, lightIndex)` форматирует номер в `.l%02d` и кладёт
карту в слот `slot` (0 или 1). Байты света ни одна функция DLL потом не
читает: их забирает тот, кто включил заголовок класса (рендерер открывает файл
сам). Направления солнца из заголовка тоже только копируются в объект и
пишутся обратно. Запросы высоты их не используют.

`Close(false)` отпускает пять слотов и заголовок не трогает. `Close(true)`
после этого перезаписывает `.hd`.

## Флаги `.sq` и список из `.hd`

Бит 15 — диагональ квада. Читают `GroundLevel` (оба варианта), `TraceSquareLine`
и `Export`. Формула — в [terrain.md](terrain.md).

Биты 0–2 — класс 0…7. **Проверено:** `TraceSquareLine` (`10003197`) и
`GroundLevel` с `TraceResult` (`10003869`) пишут `flags & 7` в
`TraceResult+0x24`. Других операций над этими битами нет: ни сравнения с
таблицей, ни выбора текстуры. Имя класса DLL не знает.

Бит 11 не читается ни одной командой. Маска `0x800` в коде не встречается.

Тридцать `int` со смещения `.hd` 520. **Проверено:** их читает только `Open`
(в `this+0x270`) и пишут `Create` / `ResetHdr` / `Close(true)`. Ни один запрос
по ним не индексируется. Связь «номер слоя текстуры → класс» из
[terrain.md](terrain.md) этой DLL не подтверждена и не опровергнута.

## Что не разобрано

- Полная арифметика пересечения луча с треугольником в `TraceSquareLine` и
  коэффициенты ориентации в `+0x14` (кроме того, что среди них есть `64`).
- Имена режимов `OpenMapFile` и виртуальных методов handle (`+0`, `+0x0C`,
  `+0x10`).
- Формат файла `Export` после тега `MESH`.
- Длина буфера пути и точный `sizeof(TERRAIN_DATA)`.
- Смысл пары `i16` по `+4` и `+6` записи `.vb`, когда она не совпадает с
  уровнем воды.
- Кто пересчитывает `.bx` после правки высот. В DLL такого кода нет.
- Как `Renderer.dll` выбирает слот света и читает байты `.lNN`. Из импорта
  видно только `OpenLight` и `GroundLevel`.

## Вторая игра

`legacy/Echelon Wind Warriors/Terrain.dll`, 29 октября 2002, 36 864 байта,
`.text` 0x5000 вместо 0x3000. Те же 21 метод плюс два:

| Ord | RVA | Сигнатура |
| --- | --- | --- |
| 22 | `0x4380` | `IRObjectsData* openRandomObject()` |
| 23 | `0x42D0` | `bool saveRandomObject()` |

В декорированных именах `VLine` переименован в `Line`, `VECTOR` — в
`Vec3<float>`. Число и типы аргументов те же. Бит 15 и маска `& 7` на месте
(`100015C6`, `100016E6`, `100020E8`). Заголовок по-прежнему читается куском
`0x20C`. Константы шага `0.2`, `1/64`, `1/256` в запросах не менялись по
смыслу; адреса констант другие, побайтово таблицы не сличались.

Хвост объекта сдвинут (**проверено** по `Open` / `openRandomObject`):

| Смещение | Было | Стало |
| --- | --- | --- |
| `+0x2F0` | указатель на конец пути | `IRObjectsData*`, кэш россыпи |
| `+0x2F4` | буфер пути | указатель на конец пути |
| `+0x2F8` | — | буфер пути |

`chunksX` по-прежнему на `+0x64`. Слоты `.sq` / `.bx` / `.vb` во второй сборке
по полям заново не размечались.

`openRandomObject`: если кэш в `+0x2F0` уже есть, увеличивает счётчик
(`vtable+4`) и возвращает его. Иначе дописывает `.ros` (`1000716C`), зовёт
`UniVars!_CreateUnifiedVariableDB@12` с ключом `0x9A1FD1C7` и ищет блок
`0x5766773F`. `saveRandomObject` пишет этот блок обратно и при пустом кэше
возвращает `false`.

Ключи, которые парсер реально пушит (**проверено** адреса строк): `Items`,
`Density`, `Dispersion`, `DensityDisp`, `Normalize`, `ObjectName`, `Distance`,
`TranspDist`, `Name`, `Red`, `Green`, `Blue`, суффикс `_Im0`, заглушка
`>>NoName<<`. Рядом лежат `float` `0.5` и `0`. Это обвязка над `EVG1` из
[evg.md](evg.md), не новый бинарный формат. Раскладку полей `IRObjectsData`
дальше имён ключей не восстанавливал.

Импорт другой: заголовок и куски россыпи идут через `CreateFileA` / `ReadFile` /
`WriteFile` / `HeapAlloc`, большие карты — по-прежнему `OpenMapFile`.
`_HFILE` больше нет. Добавлены `CRC32` и `CreateUnifiedVariableDB`.
`ClipVector` принимает `Vec3<float>`.

`Renderer.dll` второй игры импортирует уже четыре символа (у первой — два).
Какие именно, по имени не выписывал. `StdLogic.ai` `Terrain.dll` по-прежнему
не импортирует: `AvoidTerrain` остаётся именем поведения, не функцией земли.

## Как воспроизвести

Дамп первой DLL уже лежит в `tools/temp/terrain_disasm.txt` (UTF-16). Повторно:

```
dumpbin /disasm /exports /imports legacy\Echelon\Terrain.dll |
  Out-File -Encoding utf8 tools\temp\terrain_dll_disasm_utf8.txt
```

`dumpbin` —
`VC\Tools\MSVC\14.44.35207\bin\Hostx64\x86\dumpbin.exe`. Обычный `>` в
PowerShell пишет UTF-16.

Дальше, из корня репозитория:

- `python tools/temp/terrain_dll_map.py` — экспорты, слоты импорта, границы
  функций;
- `python tools/temp/terrain_dll_slice.py <va> <va> tools/temp/out.txt` —
  один диапазон адресов;
- `python tools/temp/terrain_consts.py legacy\Echelon\Terrain.dll f:10005138 d:100051A0`
  — константа по VA;
- `python tools/temp/terrain_dll_bx2.py` — сверка `.bx` с 5×5 отсчётами
  Continent.

Вторая DLL: `tools/temp/terrain_dll_ww_disasm.txt`, строки и кусок
`openRandomObject` снимает `python tools/temp/terrain_dll_ww.py`.
