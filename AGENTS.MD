# Echelon — заметки для агентов

Любительский некоммерческий ремейк аркадных авиасимуляторов «Шторм» / *Echelon*
(Steam 311080) и «Шторм: Солдаты Неба» / *Echelon: Wind Warriors* (Steam 311100).
Оригинал: движок MADia «Storm», DirectX 7, исходников нет. Всё, что мы знаем
о форматах, получено реверс-инжинирингом файлов данных.

## Цели и ограничения

- Сохранить сюжет, озвучку и аркадную авиамодель оригинала; графика новая
  (лучше освещение, простые шейдерные эффекты — ничего сложного).
- Позже: физика обломков, правка баланса. **Отложено пользователем:** геймпад,
  авто/быстрые сохранения — не делать без явной просьбы.
- `legacy/` (установленные игры) и `assets/legacy/` (всё извлечённое из них) —
  только референс, **никогда не коммитить** (уже в `.gitignore`). В репозитории
  живут только наши собственные ассеты (`assets/data`, `assets/shaders`,
  `assets/textures`) и инструменты извлечения.
- Общение с пользователем — на русском. Код, комментарии и лог — на английском.

## Стек и сборка

- C++20, CMake ≥ 4.0, Visual Studio 2022 (x64). Флаги `/W4 /WX` (см. `cxxflags.cmake`,
  INTERFACE-таргет `ECH_CXX_FLAGS`) — предупреждения ломают сборку.
- OpenGL 4.1 core (кросс-платформенно, Direct3D отклонён), загрузчик **GLEW**
  (статический, `ext/glew`, бинарники предоставляет пользователь), GLFW, GLM,
  stb — всё из `ext/`. Шейдеры `#version 410 core`.
- Boost 1.90 модульный checkout (`C:\Utils\boost\boost-1.90.0`, переопределяется
  `ECH_BOOST_SOURCE_DIR` / `BOOST_ROOT`), подключается через `add_subdirectory`
  с `BOOST_INCLUDE_LIBRARIES json test`. Данные — **JSON через Boost.JSON**
  (YAML отклонён). Тесты — Boost.Test, один бинарник `master-test-suite`.
- Команды:
  - конфигурация: `cmake\gen-msvc17-x64.bat` → `build-x64-msvc17/`
  - сборка: `cmake --build build-x64-msvc17 --config Release --parallel`
  - тесты: `.\build-x64-msvc17\tests\Release\master-test-suite.exe`
  - запуск: `.\build-x64-msvc17\src\app\Release\echelon.exe` (рабочая директория — корень репо,
    иначе `--assets <dir>`).
- Python в системе есть, но **без numpy** — вспомогательные скрипты только на stdlib.
- В PowerShell inline `python -c "..."` со скобками/кавычками ломается — временные
  скрипты писать в `$env:TEMP` и запускать оттуда. Для кириллицы:
  `$env:PYTHONIOENCODING="utf-8"`.

## Структура

- `src/core` — `echelon_core` (без зависимостей от GL): лог (`ech::log`),
  `math/curve` (кусочно-линейная кривая), `math/frame` (конвертация систем
  координат оригинала), `math/color` (sRGB ↔ линейный, пропускание тумана),
  `data/craft_spec` (JSON → `CraftSpec`),
  `sim/flight` (аркадный интегратор), `sim/fixed_step`.
- `src/app` — исполняемый `echelon`: `platform/` (окно GLFW, ввод), `render/`
  (шейдер, меш, текстура, `Model` — загрузчик экспортированных моделей, камера,
  болванка самолёта), `app.cpp` — цикл песочницы.
- `tests/` — Boost.Test; `tools/legacy_export.py` — экспортёр оригинальных данных.
- `assets/data/crafts/*.json` — наши характеристики самолётов (значения из
  `gdata.dat`, ключи snake_case).

## Соглашения движка (правая система, как в OpenGL)

- X вправо, **Y вверх, нос смотрит в −Z**. Курс 0° = −Z, положительный курс —
  поворот вправо. Лицевые треугольники — против часовой стрелки, `GL_CULL_FACE`
  включён.
- Ориентация: `yaw(−heading, Y) · pitch(pitch, X) · roll(bank, Z)` — знак у yaw
  минус именно из-за правой системы (см. `FlightState::orientation`, тест
  `forward_matches_orientation_quaternion`).
- Симуляция — фиксированный шаг 120 Гц (`FixedStep`), рендер — переменный.
- Управление: визир мыши → aim в [−1, 1]; W/S газ, LShift/LCtrl — полный/ноль,
  Esc — выход, R — сброс.
- Камера преследования сглаживает **смещение относительно самолёта**, а не
  мировую позицию (иначе на скорости отстаёт на `v / followRate` метров).

## Конвертация данных оригинала → наша система (один раз при экспорте)

В оригинале **две разные системы координат**. Эталон — `ech::meshToEngine` и
`ech::d3dToEngine` в `src/core/include/echelon/math/frame.hpp` (тест
`tests/frame_test.cpp` на `ViewDelta`, `BackViewDelta` и узле стекла BF-1).
`tools/legacy_export.py` (`to_engine`, `d3d_to_engine`) повторяет их и должен
не расходиться:

1. **Вершины `mesh.dat`** — правая система с «верхом» по −Y: X вправо, **Y вниз**,
   нос +Z, левая сторона −X (фонарь и голова пилота в −Y). Это наша система,
   повёрнутая на 180° вокруг X. Функция `to_engine`: `(x, y, z) → (x, −y, −z)` —
   **поворот, не зеркало**, порядок индексов треугольников **не меняется**,
   лицевые грани против часовой (проверка `_faces_normal` — 100% треугольников).
   Текстурные координаты: `v → 1 − v` (согласовано с
   `stbi_set_flip_vertically_on_load(1)`).
2. **Всё остальное** (`objects.dat` — позиции узлов; `gdata.dat` — `ViewDelta`,
   `BackViewDelta = (0, 1, −6)` «выше и сзади», `Position`; точки подвески) —
   классическая левая система D3D: X вправо, **Y вверх**, нос +Z. Функция
   `d3d_to_engine`: `(x, y, z) → (x, y, −z)`. Доказательство: bbox узла `CoPilot`
   в `objects.dat` = bbox меша с инвертированным Y; узел стекла ложится ровно на
   интерьер `kabina`.

Ошибочные версии, к которым не возвращаться: `z → −z` + перестановка индексов
для вершин (модель вверх ногами); `to_engine` для позиций узлов (детали
зеркалятся по вертикали).

Движок ничего не переворачивает на лету. Для новых данных из оригинала (точки
подвески, координаты объектов миссий, повороты) использовать `d3dToEngine`;
углы поворота вокруг X и Y при таком зеркале меняют знак, вокруг Z — нет.
Для координат мира миссий правило ещё нужно подтвердить.

## Форматы оригинала (разобрано)

Все пути ниже — внутри `legacy/Echelon/Data/`.

- **Контейнер** (`mesh.dat`, `textures.dat`, `materials.dat`, `objects.dat`,
  `boxes.dat`; магики `DATA/MEOS/TEXS/DMAT/DXMC/PARS`): заголовок
  `u32 magic, u32 count, u32 dataBytes, u32 nameTableBytes`; затем `count ×
  {u32 hash, u32 nameOffset, u32 size, u32 offset}` (отсортировано по hash);
  таблица имён (cp1251, через NUL) лежит **в конце файла**
  (`EOF − nameTableBytes`). Реализация — `Container` в экспортёре.
- **Меш** `<file>_<part>_Im<damage>_Ld<lod>`: `u32 0, nSubsets, nMaterials, 1;
  f32 sphere x,y,z,r; nMaterials × {flags, textureHash, materialHash, 0};
  nSubsets × {u32 prim=4 (trilist), u32 mat, u16 firstVertex, u16 vertexCount,
  u32 indexCount}; u32 ?, u32 totalVerts, u32 crc; u16 indices`. **Индексы
  каждого сабсета отсчитываются от его `firstVertex`** (без этого все сабсеты,
  кроме первого, собираются из чужих вершин — «шипы»). Вершины в
  записи `<...>_V00` (у `ha_hvy4` — `<...>_Vert00`): 32 байта
  `{f32 pos[3], normal[3], uv[2]}`.
  `Im0/Im1/Im2` — состояния повреждений (у кабины и `CoPilot` бывает ещё `Im3`),
  `Ld0..` — LOD. У части машин фюзеляж записан без имени части
  (`ha_bf2_Im0_Ld0`); экспортёр называет такую часть `HULL`.
  `textureHash = 0xFFFFFFFF` — без текстуры (стекло).
- **Текстура**: заголовок 56 байт (`u32 size @0, width @16, height @20, FourCC
  @48`), затем цепочка мипов DXT1/DXT5. Декодер — `decode_dxt`.
- **`gdata.dat`** — текстовая БД юнитов внутри бинарника
  (`[STORM CRAFTS DATA FILE V1.1]`, `Craft("Human_BF1") { … Root("HULL")
  FileName="ha_bf1" Part("LE") Position=(-2,0,0) … }`, кривые вида
  `ThrustCFromAlt (0 2.2)(100 1)(1200 .85)(1500 .25)`). Парсер —
  `parse_craft_hull`.
- **`boxes.dat`** — коллизионные оболочки по частям (сфера + набор плоскостей),
  не трансформы.
- **`objects.dat`**, запись `<file>` (для BF-1 `ha_bf1`, 9852 байта): заголовок
  `u32 ×4 (2048, offA, offB, offNames), f32 bbox (−x, −z, +x, +z)`; далее **узлы
  частей**: N записей состояний по 40 байт `{f32 bboxMin[3], bboxMax[3], radius;
  u32 ×3}`, затем `{f32 position[3], forward[3], up[3]; u32}` и 8-байтовая метка
  (короткое имя `HTNO`/`LD`/`RD`/`LV`/`RV` или хеш). **Позиция узла — относительно
  родителя**; родитель определяется именем меша (`LE_LW` → `LE`, `cockpit_glass` →
  `cockpit`). Проверка: `2.838 + 3.548 + 2.133 = 8.519` = полуразмах из заголовка.
  **Узлы бывают повёрнуты** (у BF-1 все единичные, у BF-2/BF-3/HVY крылья
  лежат с `forward=(0,1,0), up=(0,0,−1)`, у HVY3 — произвольные углы), поэтому
  `parse_object_nodes` сканирует запись с шагом 4 байта и принимает любую
  ортонормированную пару `forward/up` (те же числа читаются ещё и на +4 байта —
  это ложное эхо, берётся более ранний узел). Узлы без bbox — точки подвески,
  для частей не используются. Сопоставление с мешами — `assign_nodes`: жадное
  один-к-одному по bbox (допуск 0.25), зеркальные пары LE/RE различаются
  знаком X узла и буквой L/R в имени. Размещение части — композиция
  `pos = pos_parent + R_parent·local; R = R_parent·R_local` по цепочке имён до
  корня (`absolute_transform`); поворот переводится в нашу систему
  сопряжением `D·R·D`, `D = diag(1,1,−1)` (`_d3d_rotation_to_engine`) и
  пишется в JSON как кватернион `orientation: [x, y, z, w]`
  (`Model::Part::orientation`, `translate(offset) · mat4_cast(orientation)`).
  В хвосте записи — имена точек подвески (`MEDIUMA`, `SMALLA`, `ROCKETA/B`,
  `Duza*`), их позиции ещё не разобраны.
- **`Position` в `gdata.dat` — не размещение мешей** (это, видимо, точки
  попадания/крепления); используется только как запасной вариант.
- BF-1 (`ha_bf1`): фюзеляж хранится как часть `cockpit`. Узлы (D3D-система,
  относительно родителя): `LE`(−2.84, −0.25, −2.98), `RE`(2.88, −0.25, −2.98),
  `LW`(−3.55, −0.94, 0.62) от `LE`, `RW`(3.53, −0.94, 0.62) от `RE`,
  `glass`(−0.04, −0.35, 3.97) — стеклянный нос, `Pilot`(−0.07, −0.68, 4.89),
  `CoPilot`(−0.03, −1.46, 0.0), `cockpit`(0.07, 0.06, 0). `cockpit_CoPilot` — катапультировавшийся
  пилот на дельта-крыле (единственный с состоянием `Im3`) —
  **скрыт по умолчанию** (`HIDDEN_BY_DEFAULT` в экспортёре, `"visible": false`).
  Текстуры: `ha_bf1` (обшивка, DXT1), `asrez` (срез сопла), `kabina` (кабина,
  DXT5), `pil1m` (пилот). В `textures.dat` есть и `ha-bf1` 512×512 (через дефис) —
  та же раскладка в высоком разрешении; это единственная такая пара во всём файле,
  меш ссылается на 256×256 `ha_bf1`.
- **`materials.dat`** — записи по 68 байт в раскладке `D3DMATERIAL7`: diffuse,
  ambient, specular, emissive (по 4 f32 RGBA) + f32 power. Меш ссылается на
  материал по `materialHash`. Четвёртое значение diffuse — **не обычная альфа**:
  `Metal` 2.0, `RMetal`/`Cockpit` 0.0, `Glass` 0.4. Прозрачным считаем только
  значение строго в (0, 1) (`Model::Subset::transparent`).
  BF-1: `Metal`, `RMetal` (срез сопла), `Cockpit` (кабина), `Glass`.
- Экспортёр проверяет каждый треугольник против нормалей (`_faces_normal`) и
  печатает `!` с количеством несогласованных — должно быть 0; ненулевое значение
  означает ошибку в индексации или в конвертации осей.
- DXT5-альфа у `kabina` действительно нулевая в данных (`a0=0, a1=1`, биты 0 во
  всех блоках) — не ошибка декодера; альфа этой текстуры не используется.

## Наш формат экспорта

`python tools\legacy_export.py [--craft Human_BF1|all --lod 0 --damage N]` →
по файлу на каждое состояние, которое есть в `mesh.dat` (без `--damage` —
все): `assets/legacy/models/<file>_im<N>.model.json` (`parts: [{name, mesh,
parent, position (абсолютная, в системе корня модели), orientation
(абсолютный кватернион x,y,z,w), local_position (относительно родителя),
textures, materials, visible}]`),
`assets/legacy/models/<file>_im<N>_<part>.emesh`,
`assets/legacy/textures/<tex>.png`. `--craft all` обходит каждый `Craft("...")`
в `gdata.dat` и пропускает те, у чьего `FileName` нет записей меша.
Смещения считаются один раз по целому мешу (`Im0`) и переиспользуются: у
повреждённой геометрии другой bbox, и узел `objects.dat` по нему не находится.

EMSH v2: `'EMSH', u32 version=2, u32 nVerts, u32 nIndices, u32 nSubsets,
nSubsets × {u32 firstIndex, u32 indexCount, char texture[64], char material[64],
f32 diffuse[4], f32 specular[3], f32 power}, nVerts × 8 f32 (pos, normal, uv),
nIndices × u32`. Читает `src/app/render/model.cpp`; при несовпадении версии
модель не грузится с подсказкой перезапустить экспортёр. Если модель не
экспортирована, песочница показывает болванку `makePlaceholderCraft()`.

Рендер модели: сначала непрозрачные сабсеты, потом прозрачные (diffuse alpha в (0, 1))
с блендингом и выключенной записью глубины; diffuse материала идёт в `uTint`,
альфа — в `uAlpha` шейдера `lit.frag`.

## Цвет и освещение (линейное пространство)

- Весь свет считается в **линейном RGB**. Альбедо грузится как `GL_SRGB8_ALPHA8`
  (`Texture(path, ColorSpace::Srgb)` — значение по умолчанию; для масок/данных
  явно `ColorSpace::Linear` → `GL_RGBA8`). Кадровый буфер — sRGB:
  `GLFW_SRGB_CAPABLE` + `glEnable(GL_FRAMEBUFFER_SRGB)` в `platform/window.cpp`.
  **Не гейтить** включение по `GL_FRAMEBUFFER_ATTACHMENT_COLOR_ENCODING`: WGL
  для окна отвечает `GL_LINEAR`, хотя кодирование работает (проверено на машине
  пользователя; условная версия давала тёмный кадр).
- Любая константа цвета, подобранная на глаз (небо, тинты, цвет визира, diffuse
  из `materials.dat` — он умножал гамма-кодированные текселы) — это sRGB-значение,
  его один раз переводит `ech::srgbToLinear` (`src/core/include/echelon/math/color.hpp`,
  тест `tests/color_test.cpp`). В шейдеры sRGB-числа не попадают: `lit.frag`
  получает `uSunColor`, `uSkyAmbient`, `uGroundAmbient`, `uFogColor` уже
  линейными (структура `Atmosphere` в `app.cpp`), `glClearColor` — линейное небо.
- Туман — физический Бугер–Ламберт в линейном пространстве:
  `T = exp(−σ·dist)`, `color = mix(fogColor, color, T)`; `σ = 0.000085 1/м`
  (оптическая толщина 1 на ~12 км). Прежний коэффициент `0.00012` подгонялся
  под смешивание в sRGB и больше не годится.

## Отладка

- `echelon.exe [--craft <file>] [--damage N] [--show-hidden]
  --screenshot <file.png> [--frames N] [--cam-dist <m>] [--cam-orbit <deg>]`
  — детерминированный кадр (мышь игнорируется, лёгкий правый вираж) и выход.
  `--craft` — имя файла меша (по умолчанию `ha_bf1`); неизвестное имя даёт
  болванку. `--cam-orbit` вращает камеру вокруг самолёта и наводит её на него.
  В окне клавиши `1`…`4` переключают состояния `im0`…`im3`, если файл есть.
- Проверку данных (обход треугольников против нормалей, содержимое записей)
  удобнее делать stdlib-скриптами поверх `Container` из экспортёра.

## Открытые вопросы

- Сборка BF-1 подтверждена пользователем: ориентация верная, части на местах.
  После поддержки повёрнутых узлов собираются и BF-2, BF-3, BF-4, SF-1, CC,
  HVY1–5, грузовые (`--craft all`: 21 экспортировано, 7 пропущено). Пользователь
  подтвердил: большинство грузится, **у ряда моделей остались баги сборки —
  бэклог**, разбирать по конкретным кадрам. Известное: в `ha_cargo2` есть
  вложенный набор частей `ant_*` (тот же корпус, что `ha_cargo2_ant`) без узлов
  в `objects.dat` — они падают на `Position` из `gdata` и стоят неверно; у HVY3
  крылья/`LWA`/`RWA` с неосевыми поворотами — проверить визуально.
- У ванов (`Velian_BF1` и др.) `FileName` вроде `va_bf1` не имеет записей в
  `mesh.dat` первой части — меши, видимо, в данных второй игры.
- Разобрать позиции точек подвески в хвосте записи `objects.dat` (нужны для
  стрельбы и струй сопел `Duza*`).
- Дальше по плану: стрельба, ландшафт из сетки NetArena, скрипты миссий,
  обломки (Jolt), звук/озвучка из локальной некоммитимой папки.
